# Decision Log

FlowDeck 백엔드 개발 중 확정한 주요 설계 결정과 그 이유를 기록합니다.

이 문서는 단순 작업 목록이 아니라, 왜 해당 방향을 선택했는지와
추후 어떤 영향을 고려해야 하는지를 남기기 위한 문서입니다.

---

## 1. 파일 저장과 버전 저장 분리

### 결정

파일 저장과 버전 저장을 분리합니다.

- 코드 저장: 현재 파일 내용만 갱신
- 버전 저장: 사용자가 명시적으로 버전 저장 버튼을 눌렀을 때만 버전 생성

### 이유

`Ctrl + S` 또는 저장 요청이 발생할 때마다 버전을 생성하면
짧은 시간 안에 의미 없는 버전이 많이 쌓일 수 있습니다.

Web IDE에서는 사용자가 코드를 자주 저장할 가능성이 높기 때문에,
현재 내용 보존과 의미 있는 변경 이력 관리를 분리하는 편이 더 적합합니다.

### 반영 내용

- `project_files.current_content`에 현재 파일 내용을 저장합니다.
- `project_files.edit_revision`으로 현재 내용 수정 횟수를 관리합니다.
- 명시적 버전 저장 시에만 `file_versions.version_number`가 증가합니다.
- 파일 상세 조회 응답은 현재 내용을 바로 열 수 있도록 `content`를 포함합니다.

### 영향

프론트엔드는 일반 저장 버튼 또는 `Ctrl + S`와
버전 저장 버튼을 UI에서 분리해야 합니다.

## 2. baseRevision / editRevision 기반 저장 충돌 감지

### 결정

파일 저장 요청에 `baseRevision`을 포함하고,
서버의 현재 `editRevision`과 다르면 저장을 거부합니다.

### 이유

여러 사용자가 같은 파일을 열고 편집할 수 있는 협업 IDE 구조에서는
나중에 저장한 사용자의 내용이 이전 사용자의 변경을 덮어쓸 위험이 있습니다.

초기 MVP에서 실시간 코드 동기화까지 구현하지 않더라도,
최소한의 낙관적 충돌 감지는 필요합니다.

### 반영 내용

- 저장 요청 DTO에 `baseRevision`을 포함합니다.
- 저장 성공 시 `editRevision`을 증가시킵니다.
- 충돌 발생 시 `409 FILE_409` 응답을 반환합니다.
- 파일 상세/저장/버전 응답에 `editRevision`을 포함합니다.

### 영향

프론트엔드는 파일을 열 때 받은 `editRevision`을 저장 요청의 `baseRevision`으로 보내야 합니다.

충돌 응답을 받으면 사용자가 최신 파일을 다시 불러오거나,
자신의 변경 내용을 별도로 보존할 수 있는 UI를 제공해야 합니다.

### CRDT 미도입에 따른 동시 편집 범위

현재 MVP에서는 Yjs/CRDT 기반 실시간 코드 병합을 도입하지 않습니다.

따라서 같은 파일을 여러 사용자가 동시에 열고 편집할 수는 있지만,
서버는 저장 시점에 `baseRevision`과 `editRevision`을 비교해
오래된 기준의 저장 요청을 `409 FILE_409`로 거부합니다.

이 방식은 실시간 병합이나 편집 잠금을 제공하지는 않지만,
다른 사용자의 변경 사항을 조용히 덮어쓰는 문제를 방지합니다.

같은 파일을 누가 편집 중인지 표시하는 presence,
파일 저장/복원 WebSocket 알림,
저장 전 충돌 가능성 선제 경고는 후속 WebSocket 영역에서 검토합니다.

먼저 편집한 사용자에게 우선권을 주는 lock 방식은
낙관적 충돌 감지가 아니라 soft lock 또는 비관적 락 계열에 가깝습니다.

해당 lock 정책은 Redis TTL, heartbeat, disconnect 처리, 프론트 UX 합의가 필요하므로
현재 MVP 범위에서는 도입하지 않습니다.

### 파일 메타데이터 변경 범위

`editRevision`은 파일 내용 변경을 기준으로 관리합니다.

따라서 파일 이름 변경과 파일 이동은 현재 MVP에서 `editRevision`을 증가시키지 않습니다.

이름 변경과 이동은 파일 내용 충돌이 아니라 파일 트리/메타데이터 변경에 가깝습니다.

이를 `editRevision`에 포함하면 파일 내용이 바뀌지 않았는데도
사용자의 저장 요청이 내용 충돌처럼 거부될 수 있습니다.

파일 이름 변경, 이동, 삭제 성공 후 다른 사용자의 파일 트리를 갱신하는 흐름은
후속 WebSocket 이벤트 영역에서 처리합니다.

추후 파일 트리 충돌을 더 엄격하게 다룰 필요가 생기면
`metadataRevision` 또는 `treeRevision` 도입을 검토합니다.

## 3. 현재 파일 내용 저장 위치

### 결정

현재 파일 내용은 `project_files.current_content`에 저장합니다.

버전 이력은 `file_versions.content`에 전체 스냅샷으로 저장합니다.

### 이유

파일을 열 때마다 최신 버전을 조회해서 내용을 가져오면
파일 상세 조회가 버전 테이블에 의존하게 됩니다.

현재 내용과 버전 이력을 분리하면
파일 열기, 검색, 실행, 버전 복원 기능을 더 명확하게 확장할 수 있습니다.

### 반영 내용

- `project_files.current_content` 컬럼 추가가 필요합니다.
- 기존 `file_versions.content`는 버전 스냅샷 저장 역할을 유지합니다.
- 버전 복원 시 선택한 버전의 내용을 `current_content`에 반영합니다.

### 영향

운영 DB 적용 전 `project_files.current_content` 컬럼 마이그레이션이 필요합니다.

기존 데이터가 있는 경우 기본값 또는 초기 content 채우기 전략을 함께 고려해야 합니다.

---

## 4. 버전 이력은 전체 스냅샷 저장

### 결정

`file_versions`에는 diff가 아니라 파일 전체 내용을 저장합니다.

diff는 조회 시점에 계산합니다.

### 이유

초기 MVP에서는 복원 안정성과 구현 단순성이 더 중요합니다.

diff만 저장하면 특정 버전을 복원하기 위해
이전 패치들을 순서대로 재적용해야 하며,
중간 데이터가 깨졌을 때 복구가 어려워집니다.

전체 스냅샷 저장은 저장 공간을 더 사용할 수 있지만,
조회와 복원이 단순하고 안정적입니다.

### 반영 내용

- `file_versions.content`는 해당 버전의 전체 파일 내용을 저장합니다.
- diff 조회 API는 현재 저장된 두 버전의 content를 비교해 응답합니다.

### 영향

파일 크기가 커지거나 버전 수가 많아질 경우 저장 공간이 증가합니다.

추후 운영 단계에서 파일 크기 제한, 오래된 버전 정리,
S3 저장 전환 등을 검토할 수 있습니다.

---

## 5. 파일 저장 크기 제한

### 결정

파일 저장 요청의 content는 1MB 이하로 제한합니다.

### 이유

초기 MVP에서 DB에 파일 내용을 저장하는 구조이므로,
너무 큰 파일을 허용하면 DB 저장 공간, API 응답 시간,
메모리 사용량에 부담이 생길 수 있습니다.

### 반영 내용

- 저장 요청 content가 1MB를 초과하면 `FILE_400_3` 응답을 반환합니다.
- 파일 API 계약 문서에 제한을 명시합니다.

### 영향

프론트엔드는 제한 초과 시 사용자가 이해할 수 있는 안내 메시지를 보여줘야 합니다.

추후 대용량 파일을 지원하려면 S3 저장 또는 파일 스토리지 분리 구조를 검토해야 합니다.

## 6. Public 프로젝트 접근 범위

### 결정

현재 MVP에서는 비회원 Public 프로젝트 조회를 제공하지 않습니다.

서비스 초기 화면을 로그인/회원가입 중심 구조로 두고,
프로젝트 접근은 로그인 사용자 기준으로 처리합니다.

`PUBLIC` 프로젝트는 비회원 공개용이라기보다,
로그인한 사용자 중 프로젝트 멤버가 아닌 사용자에게도 조회 가능한 프로젝트로 정의합니다.

### 이유

FlowDeck의 핵심은 협업형 Web IDE이며,
파일 편집, 채팅, 버전 관리, 멤버 권한 관리가 모두 사용자 식별을 전제로 합니다.

비회원 접근을 허용하면 파일 내용, 버전 이력, 채팅, 멤버 목록 등
어디까지 공개할지 별도의 정책이 필요해져 MVP 범위가 커집니다.

초기 서비스 구조가 로그인/회원가입 화면에서 시작될 예정이므로,
비회원 접근보다 인증 사용자 기반 협업 흐름을 먼저 안정화하는 것이 적합합니다.

### 반영 내용

- 프로젝트/파일/버전/채팅 API는 기본적으로 인증 사용자를 기준으로 처리합니다.
- `PRIVATE` 프로젝트는 참여 멤버만 접근할 수 있습니다.
- `PUBLIC` 프로젝트는 로그인 사용자에게 조회를 허용하는 방향으로 정의합니다.
- 생성, 수정, 삭제, 저장, 복원, 채팅 전송 등 변경 작업은 멤버 권한을 기준으로 제한합니다.

### 영향

프론트엔드는 비회원 사용자를 프로젝트 내부 화면으로 진입시키지 않습니다.

추후 비회원 공개 프로젝트 탐색 기능을 추가하려면
파일 내용, 버전 이력, 채팅, 멤버 목록 공개 여부를 별도로 다시 결정해야 합니다.

## 7. 파일/버전 API 식별자 정책

### 결정

현재 파일/버전 API는 내부 Long id를 사용합니다.

프로젝트는 기존 정책대로 publicId를 URL에 사용합니다.

### 이유

초기 구현에서는 파일 트리와 버전 관리가 프로젝트 내부 리소스로만 사용되며,
외부에 독립적으로 공유되는 리소스가 아닙니다.

모든 파일과 버전에 publicId를 도입하면 API와 DB 구조가 커지고,
초기 개발 속도와 테스트 범위에도 영향을 줍니다.

### 반영 내용

- 프로젝트 식별자는 `project.publicId`를 사용합니다.
- 파일/버전 식별자는 현재 Long id를 사용합니다.

### 영향

파일 단위 공유 링크, 외부 공개, 감사 로그 고도화가 필요해지면
ProjectFile/FileVersion에도 publicId 추가를 검토할 수 있습니다.

## 8. Redis 사용 범위

### 결정

Redis는 인증 토큰 관리와 실시간 기능 보조 용도로 사용합니다.

파일 저장, 버전 저장, diff 데이터의 영속 저장소로는 사용하지 않습니다.

### 이유

Redis는 빠른 조회와 TTL 기반 임시 데이터에 적합하지만,
파일 내용과 버전 이력처럼 영속성이 중요한 데이터의 원본 저장소로는 적합하지 않습니다.

### 반영 내용

- `auth:refresh:{userId}`: Refresh Token 해시 저장
- `auth:blacklist:{sha256(accessToken)}`: 로그아웃된 Access Token 차단
- `auth:force-logout:{userId}`: 권한 변경/탈퇴 시 강제 로그아웃
- `presence:project:{projectId}`: 프로젝트 접속자 상태 후보
- `ws:session:{sessionId}`: WebSocket 세션 보조 후보
- `run:result:{runId}`: 코드 실행 결과 임시 저장 후보

### 영향

Redis 장애 시 인증/실시간 기능에 영향이 있을 수 있으므로
운영 단계에서 Redis 연결 실패 처리와 모니터링이 필요합니다.

### 보안 원칙

Redis와 JWT에는 사용자 민감 정보를 저장하지 않습니다.

JWT에는 인증과 권한 검증에 필요한 최소 식별 정보만 포함합니다.

- userId
- publicId
- authority
- issuedAt
- expiresAt

다음 정보는 JWT와 Redis에 저장하지 않습니다.

- passwordHash
- email
- name
- 사용자 전체 객체
- 파일 원문
- 프로젝트 상세 데이터

### 토큰 저장 보안 반영

현재 MVP에서는 Redis에 refresh token과 access token blacklist를 저장합니다.

단, Redis에 토큰 원문을 저장하지 않기 위해 SHA-256 해시 값을 저장합니다.

- `auth:blacklist:{accessToken}`
  → `auth:blacklist:{sha256(accessToken)}`

- `auth:refresh:{userId} -> refreshToken`
  → `auth:refresh:{userId} -> sha256(refreshToken)`

이 방식은 Redis key/value가 노출되더라도 토큰 원문 유출 위험을 줄일 수 있습니다.

Refresh token 재발급 시에는 사용자가 제출한 refresh token을 같은 방식으로 해시한 뒤
Redis에 저장된 해시 값과 비교합니다.

Access token 로그아웃 차단 여부도 원문 access token을 그대로 key에 넣지 않고,
해시 기반 blacklist key를 조회하는 방식으로 처리합니다.

## 9. Docker 기반 코드 실행

### 결정

사용자 코드는 Spring 서버 프로세스에서 직접 실행하지 않습니다.

추후 구현 시 Docker 컨테이너 기반 격리 실행을 전제로 합니다.

### 이유

사용자가 작성한 코드는 신뢰할 수 없는 입력입니다.

서버에서 직접 실행하면 파일 삭제, 네트워크 접근, 무한 루프,
메모리 과다 사용 같은 보안 문제가 발생할 수 있습니다.

### 반영 내용

현재 MVP 구현 범위에는 코드 실행 기능을 포함하지 않습니다.

추후 구현 시 컨테이너별 실행 시간, 메모리, CPU, 네트워크, 파일 시스템 제한을 적용해야 합니다.

### 영향

코드 실행 기능은 별도 실행 서비스 또는 worker 구조로 분리하는 것이 좋습니다.

## 10. 테스트 DB 전략

### 결정

현재 테스트는 H2 PostgreSQL Mode를 사용합니다.

추후 PostgreSQL 특화 기능 검증이 필요해지면 Testcontainers 전환을 검토합니다.

### 이유

MVP 개발 단계에서는 빠른 테스트 실행과 CI 단순성이 중요합니다.

H2 PostgreSQL Mode는 Docker 없이 실행 가능하고,
초기 JPA Repository 및 서비스 통합 테스트에 충분합니다.

### 반영 내용

- 테스트 profile에서 H2 기반 DB 사용
- DB/JPA가 필요한 테스트와 격리 테스트 컨텍스트 분리
- 실제 Repository를 사용해 주요 서비스 흐름 검증

### 영향

PostgreSQL partial index, 복잡한 SQL, 성능 검증이 필요해지면
Testcontainers 기반 PostgreSQL 테스트로 전환해야 합니다.
